# Deploy and release

## Company preparation

Prepare Ubuntu/Debian hosts, Docker Compose, corporate TLS and CA, DNS, an edge VIP, PostgreSQL HA and a router, separate source and audit NAS, Ollama GPU primary and standby, ClamAV with signature updates, an OIDC provider, a secret manager, a backup archive, and monitoring. `infra/ha/` contains Patroni, etcd, router, and pgBackRest configuration. The platform team must install and test that configuration. This project does not claim to create VMs, GPUs, DNS, a certificate authority, a WORM policy, or fencing from Compose alone.

Provision roles and schema from the init SQL on an empty database during an admin maintenance window, not with a runtime credential. `alembic upgrade head` must be run by a separate admin job. Runtime uses `rag_app` and `rag_worker`. Migration credentials are not mounted on the services. Every production admin and tenant DSN must use verify-full TLS and the correct CA. Application and migration DSNs use the `postgresql+psycopg://` driver. The CA path must be available on the container certificate mount. Run `SERVICE_ROLE=admin rag-admin tenant <UUID> <name>`, then `SERVICE_ROLE=admin rag-admin member <tenantUUID> <OIDC-subject> --name ... --role tenant_admin --groups hr`. There is no demo bootstrap in production. The subject must match `sub` from the official issuer. Disable a membership with `--disable`. Revoke every BFF session for a user with `SERVICE_ROLE=admin rag-admin revoke-sessions <subject>`. The effect applies on the next request and on active-query revalidation.

Register a confidential OIDC client, authorization-code with PKCE S256, audience `rag-portal`, the exact redirect `https://<hostname>/auth/callback`, profile and email scopes, and an `acr` assurance claim on the ID and access tokens. `OIDC_REQUIRED_ACR` must match the IdP MFA result. Do not fill in a number unless the IdP actually enforces MFA. The evaluation service uses a dedicated client and a dedicated membership subject, the same audience, and the minimum scope. Callback and logout must be tested with the company IdP. Portal logout revokes the local session. Global logout and IdP deactivation need a company session and revocation policy. A token that is still valid does not mean the employee is still active.

## Release pipeline

1. Publish the enterprise-rag folder as the repository root so `.gitlab-ci.yml` and the build paths match. Commit the implementation and the dependency locks. CI runs unit tests, PostgreSQL integration tests, and the React build. The Docker runner builds the image, scans HIGH and CRITICAL findings, and produces an SBOM and a digest.
2. Run the **expand** migration separately on staging, then deploy the exact image from the artifact. `$STAGING_DEPLOY_COMMAND` in CI must point at a managed deployment script on a protected runner. CI configuration, inventories, and secrets are protected variables or file variables. Do not use an untrusted merge-request runner for secrets or production.
3. Run the regression and holdout datasets, zero-tolerance security cases, the load target, and a recovery drill. Record the dataset, release, and model digests. Automatic promotion stops when evaluation fails. The production job needs a manual approval from a protected environment.
4. Fill `infra/ansible/inventory.example.yml` into a private inventory. The inventory image digest must match the CI artifact. Supply secrets from a temporary Vault export (`rag_secret_source`). Each file is mounted only on the service that needs it. Source and audit NAS must already be mounted and owned by UID 10001. The API firewall accepts only the edge. Runtime and gateway ports stay on loopback. PostgreSQL, GPU, and telemetry stay on the segments that need them.
5. Run `ansible-playbook -i <inventory> infra/ansible/release.yml` through a protected runner. The playbook rejects example hostnames and digests, pulls the image, rolls out one node at a time, and waits for readiness, including model availability and digest. HAProxy filters internal endpoints and applies TLS and rate limits. Install the TLS PEM before the HAProxy validation render. Check a canary of a few questions, plus viewer and other-tenant access, before the next node or a full promotion.
6. Watch errors, the queue, audit delivery, latency, abstention, and quality for 30–60 minutes. The release record includes the rollback image and the migration revision.

## Upgrade and rollback

LightRAG is pinned. Do not auto-update `main` in production. Make a separate release for a dependency, model, prompt, chunking, or schema-adapter change. Chunks and retrieval live in `config.py`, `rag_process.py`, `service.py`, and the index version. Reindex through the API or UI uses an immutable build namespace. When upgrading the SDK, clone a staging database from a sanitized backup and inspect the DDL and migrations the adapter performs. The first tenant database needs tenant-owner DDL. Adapter schema changes must be tested before a new runtime is rolled out.

Application rollback: drain the node from the edge, restore the previous image digest, restart the service, run readiness and a canary, then join it again. Do this only when the schema and data adapter stay compatible. Contract or destructive migrations belong in another release, after every old node has stopped and the backup has been verified. A destructive `alembic downgrade` is rejected on purpose. Rolling back a model or embedding whose index is incompatible needs a matching index snapshot or a reindex, not a model-name change. Restoring the database is a disaster-recovery procedure, not the default release rollback.

Production acceptance is unfinished until an owner signs off SSO and MFA, a pentest or threat review, real corpus and user capacity, tested failover and fencing, PITR and NAS recovery, legal retention and backup erasure, alert delivery, RPO and RTO, and on-call ownership.
